You are working on **CLINIQ: Intelligent Clinic Tracking and Monitoring System**, a clinic tracking system for Mendez Christian Academy (a Philippine private school, ~900 students, one nurse, one shared workstation, LAN-only deployment). This file is the entry point — read it before touching any code or documentation.

## Before you start any task

0. **Check the live GitHub repo (https://github.com/xKurty06/cliniq) before editing anything in the knowledge base.** Your working copy can be stale relative to GitHub (another agent may have committed changes there since), or GitHub can be stale relative to a set of local edits not yet pushed — this has already happened in both directions on this project (a formatting/loop-restructuring pass existed locally before it was pushed; a LICENSE file was added directly on GitHub before it was reflected in the vault). Reconcile before proceeding — don't assume either copy is automatically current. **Exception: `CLINIQ-Knowledge-Base/08-Logs/`** (Changelog.md, Agent-Sessions/) — these are append-only by nature, so this reconciliation isn't necessary there the same way; new entries just get added on top, they don't need to be diffed against a prior state the way a rule or a decision document does.

0a. **Separately: if you're a human copying a zip export of this project (generated by a chat session with an AI) into your actual project folder, never copy `cliniq-frontend/` or `cliniq-backend/` from that zip once real code exists in your project.** Those two folders in a chat-generated zip are organizational skeletons only (folder structure and README stub files) — the chat session doesn't write real application code. Extracting the zip on top of a project folder that already has real, built code in those folders (from Codex, Claude Code, or any coding agent) would overwrite and destroy that real code, not just overwrite something stale. Safe to copy from such a zip: `CLINIQ-Knowledge-Base/` (except `08-Logs/`, same exception as above), `AGENTS.md`, `CLAUDE.md`, `README.md`, `LICENSE`, `.gitignore`, `.claude/skills/`. This is a distinct concern from Step 0 above — Step 0 is about reconciling documentation between two live locations; this is about not letting a one-time export destroy real code that was never in that export to begin with.

- **Be cost-conscious — this is a real, standing instruction, not a suggestion:**
  - Prefer a mid-tier model for pattern-following work (most of Phase F2's screens, once the 5 reference screens establish the patterns) and reserve the most capable model for genuinely foundational or ambiguous work (the reference screens themselves, Phase 0's reasoning, an unclear Phase 2 Audit finding).
  - Don't re-run `Frontend-Loop-Engineering.md`'s Phase 0 (Changelog/Decisions/Issues/skills read-through) more than once per continuous session — only redo it when starting a genuinely fresh session or after a real gap, not before every individual screen.
  - Edit files surgically (a targeted patch to the specific line/section that changed) rather than rewriting a whole file to make a small change — checking one box in a 200+ line checklist should cost a few lines of diff, not the whole file re-output.
  - Prefer a deterministic tool over an AI reasoning pass wherever one exists: run the actual test suite instead of re-verifying by inspection, use an accessibility CLI (e.g., axe-core) for contrast/ARIA checks instead of eyeballing them. This project's own precedent: the SRS diagrams were validated by actually running them through Mermaid's parser, not just visually inspected. (No formatter/linter is prescribed by this project — the team uses its own; don't introduce one as part of "being efficient.")
  - Not every change needs the full Phase 0→1→2 process — a one-line copy fix or a correction to an already-audited screen's known value doesn't need a fresh Phase 0 and a full Countercheck. Use judgment on scale, but don't skip the process for anything that actually touches a documented requirement, a shared component, or cross-screen behavior.

## Timestamps — required on every log entry, changelog line, and ADR

Every entry you write — a session log, a changelog line, an ADR's Date field — must carry the **actual day of week, date, and time**, pulled from your real system clock at the moment you write it (e.g. `date "+%A, %B %d, %Y — %H:%M"` in bash, or whatever equivalent your environment gives you). Never estimate, round, or omit it, and never leave a placeholder. If your environment genuinely has no clock access, say so explicitly in the entry rather than guessing a value — an honest gap is fine; a fabricated timestamp is not.

## Source of Truth (conflict resolution)

1. Canonical documents (Project Plan, Modules & Features, Frontend Context Brief, Frontend Design Reference, Related Systems Review) — authoritative for **what** the system should do
2. `CLINIQ-Knowledge-Base/06-Decisions/` — authoritative for **how** it's being built
3. Current code + `CLINIQ-Knowledge-Base/02-Architecture/` — authoritative for what **currently exists**
4. `CLINIQ-Knowledge-Base/08-Logs/` — historical context, not itself current truth
5. Temporary notes, scratch work — never authoritative
6. AI-generated suggestions — never auto-promoted; only real once approved into `CLINIQ-Knowledge-Base/06-Decisions/`

A newer approved decision always overrides an older one. AI suggestions are not requirements until a person approves them.
